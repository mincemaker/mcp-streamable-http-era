Streamable HTTP の MCP クライアントは 2026-07-28 か legacy か、どこを診断するか

想定読者：MCP サーバーとその手前の中継を、HTTP の記録から診断する人。legacy の initialize とセッションは知っている前提。

使う場面：顧客から連携された MCP サーバーの疎通確認で、legacy か新仕様かを意識するとき。

省いたもの：MCP・JSON-RPC・SSE・OAuth の基礎、stdio、HTTP+SSE の細部、Tasks と MCP Apps、一覧のキャッシュ。MCP サーバーの認証認可も扱わない。アクセストークンをすべての HTTP リクエストの Authorization ヘッダーに載せる要件は、どちらのプロトコルバージョンでも同じなので、別の資料にする。ただし、どちらでも意識しておく Origin と iss の検証は、5 節の終わりに残した。

所要時間：10 分。

検証方法：振り分けの例は examples/classify.mjs を実行した出力を貼った。仕様の要件は、sources/ に保存した原文から 1 文ずつ取り出して貼り、checks.json で照合した。

この資料は、クライアントが 2026-07-28 以降と 2025-11-25 以前のどちらのプロトコルバージョンで話しているかを 1 本目の POST から見分けられること、診断で見る場所もそれで変わることを伝える。 modern ではヘッダーと本文の食い違い、legacy ではセッションとサーバー発のリクエストを見る。 Dual-era のサーバーでは両方の経路が開いている。

modern・legacy・Dual-era は仕様の呼び名で、2026-07-28 の Terminology が定義している。

Modern: protocol versions that convey version, identity, and capabilities as per-request metadata (revision 2026-07-28 and later).
Legacy: protocol versions that establish a session with an initialize handshake (2025-11-25 and earlier).
Dual-era: an implementation that supports both modern and legacy versions.

1. 1 本の記録からプロトコルバージョンを判定する

1 本目の POST が見えていれば、それで見分けられる。 legacy のクライアントは initialize から始めなければならず、modern には initialize が無い。

The initialization phase MUST be the first interaction between client and server.

ただし、1 本目の POST で以後のバージョンが固定されるわけではない。 modern では各リクエストがバージョンを宣言し、サーバーはリクエストごとに受け入れるかを決める（Versioning）。 1 本目の POST は、サーバーが modern と legacy のどちらに対応するかを見分ける手がかりになる。

Every request carries its protocol version, and the server accepts or rejects each request independently:

途中から見た記録では、_meta → MCP-Session-Id → MCP-Protocol-Version の順に手がかりを探す。

examples/captures.json には、仕様の例をもとにした記録を 9 本入れた。 ここでは途中から見た記録の A〜F の 6 本を示す。G と H は 2 節、I は 4 節で示す。

A modern の tools/call: modern — _meta に io.modelcontextprotocol/protocolVersion
B legacy の initialize: legacy — initialize で始まる
C legacy の途中（セッションあり）: legacy — MCP-Session-Id を付けている
  応答: resultType が無い結果 → 旧版サーバーの complete として扱う
D legacy の途中（セッションなし）: legacy — MCP-Protocol-Version: 2025-06-18
E 2025-03-26 の途中: legacy — MCP-Protocol-Version が無い（2025-03-26 として扱われる）
F GET の待ち受け: legacy — GET の SSE 待ち受けは 2025-11-25 まで

D と E が、途中から見たときに迷う記録になる。 legacy でもセッションを返さないサーバーはあり、そのときは MCP-Protocol-Version の値だけが手がかりになる。

E のようにヘッダーが無い POST は、クライアント側の要件から判定する。 2026-07-28 のクライアントはすべての POST に付ける。2025-06-18 以降の legacy クライアントも、initialize の後は付ける。

Every POST request to the MCP endpoint MUST include an MCP-Protocol-Version header.

If using HTTP, the client MUST include the MCP-Protocol-Version: <protocol-version> HTTP header on all subsequent requests to the MCP server, allowing the MCP server to respond based on the MCP protocol version.

仕様に従うクライアントでヘッダーを付けないのは、ヘッダーが定義される前の 2025-03-26 だけになる。 ただし、中継がヘッダーを落としたときも同じ記録になる。同じクライアントの initialize が記録にあれば、その protocolVersion で確かめる。

ヘッダーの無いリクエストを 2025-03-26 として受け入れてよい、という要件もあるが、これはサーバー側の MAY で、記録の判定の根拠にはならない。 診断では、そのサーバーが最も古い版の扱いを受け入れているか、という観点として使う。

A server that supports clients implementing protocol versions earlier than 2025-06-18 (which did not define the MCP-Protocol-Version header) MAY treat a request that omits the header as protocol version 2025-03-26.

自分の記録を振り分けるときは、同じ形の JSON にして node examples/classify.mjs <file> を実行する。

2. Dual-era クライアントは、本文の無い 400 で legacy へ落ちる

Dual-era のクライアントは、まず modern の POST を送る。 4xx が返ったときは本文を読み、modern のエラーでなければ initialize へ切り替える（Backward Compatibility）。

On 400 Bad Request, the client SHOULD inspect the response body before falling back: modern servers also use 400 for UnsupportedProtocolVersionError, MissingRequiredClientCapabilityError, and header-validation failures.
If the body contains a recognized modern JSON-RPC error, the server speaks a modern version of MCP — retry using the advertised supported versions or correct the request, rather than falling back.
If the body is empty or is not a recognized modern JSON-RPC error, fall back to initialize and continue with the legacy version for subsequent requests.

Dual-era のクライアントが 400 で見分けるものとして、原文は UnsupportedProtocolVersionError、MissingRequiredClientCapabilityError、ヘッダーの照合の失敗の 3 つを挙げている。上の引用の 1 文目がそれに当たる。 コードは Changelog が定めていて、UnsupportedProtocolVersion が -32022、MissingRequiredClientCapability が -32021、ヘッダーの照合の失敗に使う HeaderMismatch が -32020。

Renumber the error codes introduced in this draft accordingly — HeaderMismatch -32001 → -32020, MissingRequiredClientCapability -32003 → -32021, UnsupportedProtocolVersion -32004 → -32022 — and add HeaderMismatchError to the schema, which previously existed only in transport prose.

メソッドを実装していないサーバーは、404 と -32601 を返す（Protocol Version Header）。 「modern のエラー」の一覧は原文に無いので、これで全部とは限らない。

If the server does not implement the requested RPC method, it MUST respond with 404 Not Found and a JSON-RPC error with code -32601 (Method not found).

G は modern のエラーが返った記録で、クライアントは legacy へ移らない。 H のように WAF やゲートウェイが自前の 400 ページを返すと、本文に modern のエラーが無いので、クライアントは legacy へ切り替える。

G 版が合わない modern: modern — _meta に io.modelcontextprotocol/protocolVersion
  応答: modern サーバー（-32022 UnsupportedProtocolVersion）→ フォールバックしない
H 中継が本文を差し替えた 400: modern — _meta に io.modelcontextprotocol/protocolVersion
  応答: 400 に modern のエラーが無い → initialize へフォールバック

クライアントはこの判定を、HTTP ではオリジン単位で保存する（SHOULD）。

Clients SHOULD cache the result for the lifetime of the server process (stdio) or origin (HTTP), and MAY persist it across restarts of the same server configuration, re-probing if the cached assumption later fails.

判定を保存するクライアントなら、中継が 1 回本文を差し替えただけで、以後の通信が legacy の経路に移りうる。 どこまで続くかは実装しだいになる。保存は SHOULD、再起動をまたぐ保存は MAY で、保存した前提が崩れればクライアントは調べ直す。 ここは仕様の要件を組み合わせた推論で、実際のクライアントで確かめてはいない（未検証）。案件では、主張ではなく試験の項目として扱う。

4. modern 経路の診断観点

中心は、ヘッダーと本文の食い違いになる。 中継が Mcp-Name で認可し、サーバーが本文の name で実行すると、許されていないツールを呼べる。 サーバーは食い違いを 400 と -32020 で拒否しなければならない（Server Validation）。

Servers that process the request body MUST reject requests where the values specified in the headers do not match the corresponding values in the request body.

I ヘッダーと本文が食い違う modern: modern — _meta に io.modelcontextprotocol/protocolVersion
  不一致: mcp-name: ヘッダー "read_only" ≠ 本文 "delete_all"
  応答: modern サーバー（-32020 HeaderMismatch）→ フォールバックしない

この例では、Mcp-Name を Base64 の形式 =?base64?…?= で送った。 サーバーはデコードしてから本文と比べる（MUST、Value Encoding）。 デコードせずに比べる実装や、中継だけがデコードする構成は、ここで食い違う。

In particular, servers MUST decode an encoded Mcp-Name or Mcp-Param-{Name} value before comparing it to the corresponding request body value during Server Validation.

ヘッダーで制御する中継は、MCP-Protocol-Version が古いか無いリクエストを拒否する（SHOULD）。 古い版のリクエストでは、後段がヘッダーと本文を照合しないため。

Intermediaries that enforce policy based on mirrored headers (e.g., routing or rate-limiting by tenant) SHOULD verify that the MCP-Protocol-Version header indicates a version that requires header–body validation.
If the version is older or the header is absent, the intermediary SHOULD reject the request rather than trusting unvalidated header values.

ほかの観点は次の 3 つ。

requestState を書き換えて再送する。別の利用者の state、期限切れの state、別のリクエストの state を送る 攻撃者が操作できる入力として扱う（MUST）。認可や処理に効くなら HMAC・AEAD で守り、検証に失敗した state を拒否する（MUST）。主体・有効期限・元のリクエストの照合は SHOULD。1 回限りの処理はサーバー側で保証する（MUST）。MRTR

5. legacy 経路の診断観点

Dual-era サーバーが initialize に応える限り、2025-11-25 までの攻撃面が残る。 要件は 2025-11-25 のSession ManagementとResumabilityにある。

The session ID SHOULD be globally unique and cryptographically secure (e.g., a securely generated UUID, a JWT, or a cryptographic hash).
The server MAY terminate the session at any time, after which it MUST respond to requests containing that session ID with HTTP 404 Not Found.
The server MUST NOT replay messages that would have been delivered on a different stream.
観点 対象になる条件
Session ID が推測できないか。終了後に 404 になるか（MUST）。DELETE で終了できるか initialize の応答に MCP-Session-Id が付く
Last-Event-ID で、別のストリームのメッセージが再送されないか（MUST NOT） サーバーが SSE のイベントに id を付ける
SSE 上の sampling/createMessage を、利用者が拒否できるか（SHOULD）。elicitation/create と roots/list の要件は、この資料では原文を確かめていない クライアントが legacy で、該当の capability を宣言している
modern 側と同じ認可・検証が、legacy 側にもかかっているか サーバーが Dual-era 
For trust & safety and security, there SHOULD always be a human in the loop with the ability to deny sampling requests.

Session ID が返らないサーバーでは、セッションの観点は対象外になる。 Roots・Sampling・Logging は 2026-07-28 で非推奨になったが、非推奨の期間中は動き、その期間は最短で 12 カ月と決められた（Changelog）。 残っている間は観点に含める。

These features remain fully functional during the deprecation window but new implementations should not add support for them.
Adopt a specification feature lifecycle and deprecation policy defining the Active, Deprecated, and Removed feature states, a minimum twelve-month deprecation window, and a registry of deprecated features (SEP-2596).

Origin の検証はどちらのプロトコルバージョンでも同じ。 不正な Origin には 403 を返す（Security & Endpoint）。

If the Origin header is present and invalid, servers MUST respond with HTTP 403 Forbidden.

認可レスポンスの iss の検証は、2026-07-28 で加わったクライアントの要件。 認可レスポンスに iss があれば、認可コードをトークンエンドポイントへ送る前に、記録しておいた issuer と比べる（MUST、Authorization Response Validation）。

Authorization servers SHOULD include the iss parameter in authorization responses per RFC 9207, and MCP clients MUST validate a present iss against the recorded issuer before redeeming the authorization code (SEP-2468).

2025-11-25 の Authorization には iss も RFC 9207 も出てこないので、legacy のクライアントが検証するとは限らない。 同じ不備でも、通信がどちらのプロトコルバージョンかで、指摘の種類が変わる。modern で話すクライアントが検証しないなら、MUST の実装漏れになる。legacy で話すクライアントなら要件違反ではないが、新しいバージョンでは MUST になるので、今のうちに対応しておくべき点として情報の扱いで伝えられる。 メタデータが authorization_response_iss_parameter_supported を true にしているのに iss が無い応答は、拒否する。

6. チェックリスト

  • 1 本目の POST に initialize があるか。無ければ _meta の protocolVersion を見る
  • サーバーが initialize に応えるか。応えるなら Dual-era か legacy で、5 節が対象
  • modern の POST に、本文の無い 400 を返す中継が手前にいないか
  • Mcp-Name と本文の name を食い違わせて、400 と -32020 が返るか
  • Mcp-Name を Base64 の形式で送っても、同じ判定になるか
  • MCP-Protocol-Version を消すか古くして、中継の判定が変わらないか
  • requestState を書き換え、別の利用者・期限切れ・別のリクエストで再送して拒否されるか
  • modern 専用サーバーに GET・DELETE を送り、405 が返るか
  • Session ID が返るなら、推測できない値か、終了後に 404 になるか
  • Last-Event-ID に別のストリームのイベント ID を入れて、そのストリームのメッセージが再送されないか
  • legacy のクライアントで、SSE 上の sampling/createMessage を利用者が拒否できるか
  • Origin を変えて 403 が返るか
  • クライアントが、認可レスポンスの iss を記録した issuer と違う値にされたとき、認可コードを送らずに止まるか。止まらなければ、modern のクライアントなら MUST の実装漏れ、legacy のクライアントなら情報として伝える

7. 理解度チェック

  1. 記録の途中で、MCP-Protocol-Version も _meta も無い tools/list の POST を見つけた。これは modern の不正なリクエストと判定してよいか。
答え

判定しない。仕様に従うクライアントでヘッダーを付けないのは 2025-03-26 だけだが、中継がヘッダーやメタデータを落とした場合や、仕様に従わない modern のクライアントでも同じ記録になる。この POST だけでバージョンを決めず、同じクライアントの initialize があればその protocolVersion と、中継の前後の記録で確かめる。1 節の E の記録がこの形。

  1. modern 専用サーバーを診断している。Session ID の推測を観点に入れるべきか。
答え

入れない。modern 専用サーバーは initialize に応えず、MCP-Session-Id を発行しない。代わりに、MCP-Session-Id を付けた POST が無視されること、GET・DELETE が 405 になることを見る（3 節と 4 節）。

  1. Dual-era クライアントの前に、modern のリクエストを独自の HTML の 400 で拒否する WAF がある。何が起きうるか。
答え

本文に modern のエラーが無いので、クライアントは initialize へ切り替えうる。後段が legacy に対応していれば、その経路で通信が成り立つ。modern 専用なら initialize は通らない。クライアントがその判定をオリジン単位で保存すると、以後の通信にも影響しうる。2 節の H の記録と分岐の図。仕様からの推論で、実際の切り替えと保存の動きは、クライアントの実装ごとに確かめる必要がある。

  1. modern の POST に JSON-RPC の result が返り、その中に resultType が無かった。何を疑うか。
答え

後段が legacy の意味で処理した可能性を疑う。ただ、これだけでは後段が legacy であることも、ヘッダーと本文を照合していないことも決まらない。modern サーバーの実装の不備や、中継による書き換えでも同じ記録になる。後段がどのバージョンとして受け取ったかを確かめ、Mcp-Name と本文の name を食い違わせたリクエストで、400 と -32020 で拒否されるかを別に試す（3 節と 4 節）。
